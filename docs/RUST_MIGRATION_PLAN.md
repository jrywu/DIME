# DIME Rust 移植計畫

狀態：已確認方向（2026-11-06）

## 0. 已決定事項

| 議題 | 決定 | 影響 |
|---|---|---|
| 與上游 `jrywu/DIME` 的關係 | 不追上游 | 不需要為了方便合併而保留 C++ 結構，可以直接重構或刪除 |
| 設定 GUI（DIMESettings） | 改成 Rust | 第 5b 階段要做；`DIMESettings.exe` 最終是純 Rust |
| 最終形態 | Rust 核心 + 少量 C++ | 第 4 階段不強求全部改寫：TSF 外殼可以保留為薄 C++ 層，只負責把 Rust 產生的動作套用到 TSF（2026-11-10：C++ 目標改為實際下限約 9～10k 行，見 `RUST_TSF_SHELL.md`） |

最終架構：

- `DIME.dll`：所有邏輯（設定、組字、候選字、整句、字典）與 UI 視窗在 Rust；C++ 只剩 COM 進入點、TSF／COM 介面、sink 與 edit session 的轉接（目標約 9～10k 行；原訂 ≤ 5k 需要把部分 COM 也改成 Rust，見 `RUST_TSF_SHELL.md` 1.1 節）。
- `DIMESettings.exe`：純 Rust（CLI + GUI）。
- 舊版 `ConfigDialog.cpp`（2.6k 行）：DLL 已改成啟動 `DIMESettings.exe`（`ShowConfig.cpp`），直接刪除，不移植。

## 2. 原則

1. **由下往上、由內往外**：先移植不碰 TSF 的邏輯層，最後才換 COM 外殼。每一階段結束時產品都能出貨。
2. **一律有開關、一律有對拍**：沿用字典引擎的做法——新 Rust 模組先在 C++ 介面後面以建置開關替換，預設仍走 C++；用對拍測試證明行為一致、經過至少一次發版後才把預設切到 Rust，再下一版刪除 C++ 實作。
3. **保留怪異行為**：輸入法使用者依賴肌肉記憶，任何差異都是 bug，除非刻意修正並記錄在 `docs/`。
4. **C++ 呼叫端不動**：`CConfig`、`CCompositionProcessorEngine` 等保留原本的 C++ 介面，內部改轉呼 Rust。避免同時改幾百個呼叫點。
5. **FFI 邊界不讓 panic 通過**：維持 `catch_unwind`；COM 階段每個 vtable 方法都要包住，panic 轉成 `E_FAIL`。
6. **執行環境限制**：DLL 會載入到每個應用程式（含 Store app／AppContainer、低完整性行程），所以禁止 Rust 端在 DLL 內新增執行緒、全域鎖要避免死結、檔案存取要容忍唯讀。`/MT` + `+crt-static` 的設定沿用。

## 3. 分階段計畫

### 第 1 階段：設定（`CConfig`）→ `dime-config` crate

- **內容**：每個模式的設定結構、預設值、INI 讀寫（UTF-16）、`ApplyIniConfigEntry`、各設定項的合法值檢查、模式適用性（目前分散在 `Config.cpp`、`CLI.cpp`、`SettingsController.cpp`）。
- **作法**：新增 `dime-config`，設定項以一張表（key、型別、預設值、適用模式、範圍）描述，取代目前「GUI、CLI、`CConfig` 三處要一致」的人工同步。`CConfig` 的 static getter/setter 保留，改成讀寫 Rust 端的狀態。ACL（"ALL APPLICATION PACKAGES"）與 `%APPDATA%` 路徑可先留在 C++。
- **測試**：`ConfigTest.cpp`（2.1k 行）照跑；新增「同一份 INI 由 C++ 與 Rust 讀入後所有欄位相同、寫出位元組相同」的對拍；Rust 端單元測試覆蓋每個 key 的邊界值。
- **為什麼先做**：相依最少（被大家用、自己不用別人），而且 DLL 與 DIMESettings 共用，做完後第 5 階段的 CLI 可以直接沿用。
- **進度（2026-11-06）**：
  - ✅ 1a：`rust/crates/dime-config`（設定值、預設值、`ApplyIniConfigEntry`、載入流程與 ColorMode 遷移、`WriteConfig` 輸出、CLI key 定義表與驗證）與 FFI（`dime_settings_*`）。`DIME.dll` 在 `DimeUseRustEngine=true` 時，設定的解析、預設值與寫檔改走 Rust；`CConfig` 的 static 成員仍是儲存位置。
  - ✅ 對拍：`src/tests/RustConfigParityTest.cpp`（2,201 組 INI key/值、各模式預設值、20 份 `WriteConfig` 輸出逐位元組、`LoadConfigFromFile`）。對拍時找到並修正一個差異：`CLSIDFromString("")` 會失敗，空字串不會清除 GUID（只有 CLI 會把空字串當成清除）。
  - ✅ 1b：`DIMESettings.exe`（Win32）在 `DimeUseRustEngine=true` 時連結 `dime_ffi.lib`，定義 `DIME_USE_RUST_CONFIG`：設定的預設值與寫檔、CLI `--get`/`--set` 的取值、驗證與錯誤訊息改走 Rust（字典引擎仍是 C++）。C++ 的 `g_keyRegistry` 暫時保留，`RustCliParityTest` 檢查它與 Rust 的 key 表完全一致，並對拍 `--get` 全部 key 與 `--set` 2,014 組 key/值（回傳碼、錯誤訊息、結果）。C++ 與 Rust 版 exe 的實際 CLI 輸出也逐一比對過。Rust 建置的執行期不再用 C++ 的 `g_keyRegistry`（見第 5a 階段）。這張表與 `GetKeyValue`／`ApplyKeyValue` 仍留給全 C++ 建置和 `RustCliParityTest`，刪除留到第 6 階段。
  - ✅ 1c：定義 `DIME_USE_RUST_CONFIG` 時，設定值存放在 Rust 的全域物件（`dime_settings_global()`，常數初始化、位址固定）；`CConfig` 的設定成員宣告為 `DIME_CONFIG_VALUE`、定義為 `DIME_CONFIG_DEFINE`，在此模式下變成指向該物件欄位的參考，所有 getter/setter 與 300 多個呼叫點不用改。`ReverseConversionDescription` 改由 `GetReverseConversionDescription()` / `SetReverseConversionDescriptionText()` 存取（字串在 Rust）。Rust 的操作透過 `CRustConfigScope` 直接作用在全域物件上，不再取快照與寫回。`DIMETests` 加上 `/p:DimeTestRustConfig=true` 可在此模式下跑完整測試套件（657 個全部通過，預設模式也是 657 個全部通過）。
  - ⏳ 切換預設：經過一個正式版本後，把 `DimeUseRustEngine` 改成預設開啟；再下一版刪除 C++ 的儲存、`ExportValues`/`ImportValues`、`ApplyIniConfigEntry` 與 `WriteConfig` 的 C++ 寫法。

### 第 2 階段：組字核心 → `dime-core::compose`

- **內容**：字根緩衝、`KeyStateCategory` 按鍵分類、`KeyProcesser` 的判斷、`IsVirtualKeyNeed`／`IsKeystrokeRange`、各模式規則（大易地址鍵、行列特別碼／短碼／詞彙結束鍵、注音組字與許氏鍵盤、萬用字元）、候選字清單產生與排序、繁簡轉換、`TCFreq`、`SentenceBuffer`。
- **作法**：把目前分散在 `KeyEventSink` → `KeyProcesser` → `KeyHandler*` 的決策抽成一個不依賴 TSF 的狀態機：

  ```rust
  pub struct ImeCore { /* 模式、字根、候選、整句緩衝… */ }
  impl ImeCore {
      /// 回傳「是否吃掉按鍵」與要執行的動作；不碰任何 Windows API。
      pub fn on_key(&mut self, key: KeyEvent, ctx: &Context) -> KeyResult;
  }
  pub enum Action {
      SetComposition { text: String, caret: usize, attrs: Vec<Span> },
      ShowCandidates { items: Vec<Candidate>, page: usize, selected: usize },
      HideCandidates, Commit(String), Notify(String), /* … */
  }
  ```

  C++ 的 sink／edit session 只負責把 `Action` 套用到 TSF。這一步也是第 3、4 階段的前提。
- **建議分兩步**：(2a) 先把 C++ 自己重構成「決策 → 動作」的形式（仍是 C++），補上錄製測試；(2b) 再把決策層換成 Rust。直接跳 (2b) 的話，沒有乾淨的 C++ 基準可以對拍。
- **進度（2026-11-06）**：
  - ✅ 2a-1 黃金測試：`src/tests/KeyFlowHarness.*` 在專屬 STA 執行緒上建立**真實的 TSF thread manager**，文件由自製的 `ITextStoreACP`（純文字 + 一個選取區）提供；`CDIME::_TestActivate` 走 `ActivateEx` + `OnActivated` 的引擎設定（不註冊系統 sink），按鍵依 `ITfKeystrokeMgr` 的順序送進 `OnTestKeyDown`/`OnKeyDown`/`OnTestKeyUp`/`OnKeyUp`，並設定執行緒的鍵盤狀態（Shift、CapsLock）與美式鍵盤配置。每個按鍵後記錄：是否吃掉、文件文字、選取區、組字內容、候選字模式、候選字清單與選擇。`%APPDATA%` 透過新的 `Global::GetAppDataPath()`（測試可用 `Global::testAppDataOverride` 導向）與 `%ProgramW6432%` 都指向暫存資料夾，不碰使用者的設定與碼表。IME 若當機（SEH），測試會失敗並附上呼叫堆疊，不會帶走測試主機。
  - `src/tests/KeyFlowTest.cpp` 有 40 個情境（行列／注音用安裝程式碼表；大易／自訂用合成小碼表；聯想詞用合成的 `TableTextServiceDaYi.txt`），涵蓋選字鍵、翻頁、萬用字元、符號模式、Shift 英數、最大碼長、強制特別碼、行列 40、注音倚天鍵盤、大易地址鍵與選字鍵模式、自動組字、聯想詞、整句輸入（含候選字修改）。黃金檔在 `src/tests/keyflow/*.txt`，設 `DIME_KEYFLOW_RECORD=1` 重新錄製。C++ 模式與 Rust 設定儲存模式（`DIME_USE_RUST_CONFIG`）、x64 Debug 與 Win32 Release 結果都相同。
  - 黃金測試找到的問題：
    - **已修正**：自訂模式開「自動組字」時，輸入 `a` 再輸入萬用字元 `*` 會讓宿主程式當掉（`CompositionProcessorEngine.cpp` 增量候選的字碼長度相減下溢，`CCandidateWindow::_AddString` 丟出 `std::bad_array_new_length`）。
    - **已在 2c-8 修正**：README 格式的自訂 `Phrase.cin` 查不到聯想詞。查詢時若 `Global::hasPhraseSection` 為 FALSE 會在字後加 `*`，但 CIN 的 `CollectWord` 不把 `*` 當萬用字元；這個全域旗標由任一 TTS `[Phrase]` 段落設定且從不清除，所以實際行為取決於行程先前載入過什麼。
  - ✅ 2a-2（部分）：候選字清單、選擇與翻頁從 `CCandidateWindow` 抽成不依賴 UI 的 `CCandidateListModel`（`CandidateListModelTest` 鎖定規則）；`_IsKeyEaten` 拆成 `_GatherKeyFacts`（TSF/Win32 讀取）與 `_DecideKeyEaten`（不呼叫 TSF）。
  - **方向調整（2026-11-06）**：handler 不再先完整重構成 C++ 的「判斷 → 動作」，改為**逐塊直接移植到 Rust**，每塊用開關切換、由黃金測試與對拍測試保護，避免重構一次 C++ 再丟掉。
  - ✅ 2b-1 候選字選擇與翻頁：`dime-core::candidates`（`CandidatePaging`）＋ `CRustCandidateListModel`（字串仍在 C++，Rust 只管總數、選擇、分頁）。`CCandidateListModel::Create()` 在 `DIME_USE_RUST_ENGINE` 時回傳 Rust 版。`RustCandidateListModelParityTest` 以 400 組隨機序列（24,000 個操作）比對 C++ 與 Rust。`DIMETests` 加 `/p:DimeTestRustEngine=true` 可用完整 Rust 組合（字典引擎、設定儲存、候選字翻頁）跑全部測試，40 個黃金情境結果與 C++ 相同。
  - ✅ 2b-2 按鍵分類：`dime-core::keyclass`（`classify_key`）是 `IsVirtualKeyNeed` 與其輔助函式（跳脫輸入、大易地址鍵、結束鍵、字根表、選字鍵範圍、ETEN 注音對照）的逐行移植。C++ 端 `_IsVirtualKeyNeedRust` 把引擎狀態、全域變數、設定和 Win32 讀值（`MapVirtualKey`、CapsLock、`iswprint`）打包成 `DimeKeyInput`；`IsVirtualKeyNeed` 在 `DIME_USE_RUST_ENGINE` 時改走 Rust。保留的細節：字根緩衝為 null 與空字串不同（大易 `=` 只有在後者才算跳脫輸入）、沒有 key state 時 Enter/Space 在 switch 中 fall through 而回傳 TRUE、`towupper` 只轉 ASCII。`KeyClassifyParityTest` 以 400 組隨機引擎狀態 × 500 個按鍵（共 200,000 次）比對，涵蓋 35 種結果；故意植入錯誤時第 6 個按鍵就被抓到。`_DecideKeyEaten` 的其他部分仍是 C++（會改動 `CDIME` 狀態，且與整句模式的判斷交織），留待 handler 移植時一併處理。

- **2c handler 流程（決定：Rust 主導流程）**：handler 會互相呼叫、中途向 C++ 取資料、每一步都改 TSF，無法寫成「輸入 → 步驟」的純函式。改為 `dime-core::session` 實作 handler 流程，透過 `Host` trait 操作 text service；C++ 以 `DimeHost` vtable（`src/RustSessionHost.*`，`CDIME` 的 friend）提供 TSF／UI 基本操作、狀態存取，以及尚未移植的 handler。每次搬一組 handler，原 C++ 版改名為 `_XxxCpp`，公開函式依 `DIME_USE_RUST_ENGINE` 分派。對拍靠黃金打字情境（預設建置錄製、Rust 組合比對），每組移植前先補情境。最終狀態（`_candidateMode` 等）也搬進 Rust 後，C++ 就只剩 TSF 外殼（第 4 階段）。
